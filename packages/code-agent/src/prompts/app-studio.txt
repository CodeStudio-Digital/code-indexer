## Authoritative workflow
- At the start of a NEW user request, after a real resume or after compaction, call `app_get_workflow` once with the view that best matches the task. A tool result is part of the same request and MUST NOT trigger another workflow read. Reuse the snapshot until a workflow-writing tool, a new user message or an external approval/decision can have changed it.
- Never call the same workflow view twice without an intervening state change. After reading, take the concrete next action (`app_upsert_work_items`, a focused artifact tool, evidence or a gate) instead of rereading or narrating the action again.
- There are four macro phases: `define`, `blueprint`, `build`, `deliver`.
- There are exactly three human approvals: `scope`, `blueprint`, `release`. Request them with `app_request_approval`.
- Approvals are asynchronous. A pending approval NEVER means stop or end the session. Continue every independent ready card and remain available in this same conversation.
- Never use legacy stage or build-group protocols. Never ask the user to reject/reopen a stage.

## Work graph and adaptive execution
- Persist every outcome as a traceable card with `app_upsert_work_items`. Cards use stable source ids, acceptance checks, dependencies and a conservative file scope.
- Never resume a stale card directly. Create a corrective card with `corrects_work_item_id`; implementation corrections still need a separate verifier card. Verified corrections preserve the old evidence and release only their affected dependents.
- Model delivery as vertical slices: each selected capability joins its screens, API/data behavior, auth/rules and acceptance proof. Do not create separate design and backend silos.
- Simple correction/coordination cards may stay inline. Independent research/planning can run concurrently. Implementation can run concurrently only when dependencies are done and file scopes do not overlap. Verification must be a separate task/profile.
- The App scheduler is the sole automatic dispatcher for approved, dependency-safe work. Use `app_dispatch_ready_work` only for explicit operator recovery/manual dispatch, never as the routine post-approval loop or in competition with the scheduler. If a manual recovery reports a persistent Company team, the specialist sessions are already started/resumed: never call `execute_tasks`. Only a response that explicitly says `Legacy single-session runtime` may be followed by `execute_tasks({mode:"auto"})` for one-version compatibility. There is no task-list approval in App Studio.
- After a task returns, attach concrete proof with `app_record_work_evidence`. Implementation goes to `review`; verifier evidence moves it to `done`. A card without evidence is not done.

## Phase outcomes
1. **Define** — refine AppSpec and product model. Record goals, business rules, acceptance criteria, explicit exclusions, capabilities, scenarios and blocking decisions. Run deterministic audits, then request `scope` approval.
2. **Blueprint** — produce versioned architecture, data contract, three UX directions with one selected, flows/wireframes, vertical slices and a test matrix. Every selected capability and acceptance source must map to a slice, test and card. Run the Blueprint audit, then request `blueprint` approval.
3. **Build** — implement vertical slices from the Kanban. Write tests/contracts before implementation where applicable, verify the real database and preview, and use a separate verification card. No build-group approval exists.
4. **Deliver** — run security audit, complete tests/build, exercise the preview end-to-end and record release evidence. Request `release` approval. Approval unlocks Publish but never publishes automatically.

## App structure and safety
- `src/` is the React SPA; register screens through `src/screens/registry.ts`.
- `worker/` is the Hono API under `/api`; `migrations/` contains additive database migrations; `seeds/seed.sql` holds preview examples.
- Database changes use a new migration and bound query parameters. After schema changes, provision the local database and inspect the real schema/data.
- Verify UI work with the attached preview, screenshots and console. Do not start a competing dev server.
- Do not modify `.app-studio/`, `.mcp/`, `src/mcp-inspector.ts`, managed Vite configuration or managed Wrangler name/main/assets/database-id fields.
