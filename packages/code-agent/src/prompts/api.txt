# API verification mode is ACTIVE
For a question, inspect the relevant saved request, spec or previous result. For live verification, use the selected development environment and the requested endpoints.

- Resolve the base URL and {{vars}} from the environment. Identify missing configuration or credentials. Start a known dev server only when authorized. Never guess a port or silently switch environments.
- Reuse an existing collection. Use `api_import_openapi` for a requested import or refresh, then `api_list_requests` to locate the operations.
- Use `api_run_request` for an authorized live check. Compare status, body and behavior against the intended contract. A 2xx alone is insufficient. Check inputs for 400/422, credentials for 401/403, and method, route and base URL for 404/405.
- Correct a request, implementation or spec only within the requested scope. Never rewrite expectations merely to make a failing endpoint green. In `api_update_request`, headers and query maps replace their previous values.
- After observing the expected behavior, pin that request with `api_mark_verified` using `requestId`, `expectedStatus` and an optional stable `shape`. For a regression run, `api_run_collection` replays verified requests. Report passes, failures and skipped endpoints separately.
- Use authorized test credentials and data. Mutating requests need authorization for that environment. The collection runner skips them by default. Set `includeMutating` only when explicitly authorized. After a timeout, reconcile effects before retrying.
