# Plugins

The IDE is extensible through **plugins** — Claude Code/Codex-compatible bundles that add
capabilities to the agent and the workspace. A plugin can contribute:

- **Agent tools** — JS functions the coding agent can call, run isolated in a worker thread.
- **MCP servers** — external tool providers (stdio / HTTP), registered via `.mcp.json`.
- **Skills** — prompt-based capabilities (`SKILL.md`) + slash commands.
- **IDE UI** — sandboxed tool windows (iframes), command-palette commands, activity-rail icons, themes.
- **Editor/project modules** — editor actions, status-bar items, run configurations, and detected
  project modules/facets that activate only for matching projects.
- **LLM providers** — provider metadata plus optional executable V2 adapters owned by the plugin.

Plugins install by **namespace** (the `plugin.json` `name`) from a local folder, a GitHub repo, or
the hosted **Market**. Everything a plugin adds is tracked under its namespace, so uninstall is clean.

> **Format.** A plugin is compatible with the Claude Code / Codex plugin spec
> (`plugin.json` + `.mcp.json` + `skills/`), with a proprietary `.app.json` layer for the
> IDE-specific contributions and a typed authoring SDK (`@mcp/plugin-sdk`) on top. Existing
> Claude Code plugins (skills + MCP servers) install as-is.

## Anatomy

```
my-plugin/
  plugin.json      manifest — name, version, author, interface, component paths
  .app.json        IDE contributions (GENERATED by `build` — don't hand-edit)
  .mcp.json        optional — MCP servers to register (Claude Code convention)
  skills/          optional — SKILL.md + commands/*.md (Agent Skills standard)
  src/plugin.ts    source — definePlugin({ ... }) authored with the SDK
  dist/plugin.js   built worker bundle (esbuild output of src/plugin.ts)
  ui/panel.template.html  webview entry (source) — `<div id="root" class="mcp-app">` + <script src="./src/main.ts">
  ui/src/main.ts   webview UI, built with @mcp/plugin-sdk/ui primitives
  ui/panel.html    GENERATED by `build` (self-contained, inlined) — don't edit, gitignore it
```

`.app.json` declares the IDE contributions **without executing code**, so the host can register
tool windows / commands / themes and the agent's tool list at load time. The matching tool
*handlers* live in `dist/plugin.js`, keyed by name. `mcp-plugin build` produces both from your
`definePlugin(...)`.

## Authoring (SDK + CLI)

```bash
# scaffold (run via tsx in this repo; a published bin ships later)
tsx packages/plugin-sdk/src/cli/index.ts create my-plugin
cd my-plugin                     # edit src/plugin.ts
tsx <repo>/packages/plugin-sdk/src/cli/index.ts validate .
tsx <repo>/packages/plugin-sdk/src/cli/index.ts build .      # → dist/plugin.js + .app.json
tsx <repo>/packages/plugin-sdk/src/cli/index.ts publish .    # → hosted Market (needs MCP_MARKET_URL)
```

`src/plugin.ts`:

```ts
import {
  definePlugin, contributeTool, contributeToolWindow, contributeCommand, contributeTheme,
} from '@mcp/plugin-sdk/define';

export default definePlugin({
  tools: [
    contributeTool({
      name: 'echo',
      description: 'Echo text back.',
      parameters: { type: 'object', properties: { text: { type: 'string' } }, required: ['text'] },
      mutates: false,
      handler: async (args, ctx) => ({ content: String(args.text) }),
    }),
  ],
  toolWindows: [contributeToolWindow({ id: 'panel', title: 'My Panel', side: 'right', entry: 'ui/panel.html' })],
  commands: [contributeCommand({ id: 'do-x', label: 'My: Do X' })],
  themes: [contributeTheme({ id: 'dark', label: 'My Dark', appearance: 'dark', tokens: { '--primary': '#4d8cff' } })],
});
```

Import from `@mcp/plugin-sdk/define` (zero-dep) — not the package root — so the bundle stays lean.

### Multi-file webview UI (`*.template.html`)

Webviews render as **null-origin** iframes, so the final HTML must be self-contained — external
`<script src>` / `<link href>` never load. To keep authoring modular anyway, the CLI `build`
inlines templates: any `ui/**/*.template.html` has its **relative** script/stylesheet refs bundled
(esbuild, `iife`/browser, TS supported) and spliced in, emitting the artifact without the suffix
(`ui/panel.template.html` → `ui/panel.html` — gitignore the artifact, point the tool window's
`entry` at it). Absolute/`https:` refs are left untouched. The template stays a valid HTML page you
can open in a browser while iterating. `</script>` sequences inside bundles are escaped. Plugins
without templates build exactly as before. Changes only reach the app after **reinstall** (the
contributions snapshot lives in `installed_plugins`).

### Contribution points

| `contributeX` | Surface | Notes |
| --- | --- | --- |
| `contributeTool` | Agent tool `plugin__<ns>__<name>` | `handler(args, ctx)` runs in an isolated worker. `ctx` = `{ projectName, cwd, fetch, log, host.invoke }` — no `fs`/`child_process`. |
| `contributeToolWindow` | Sandboxed iframe + rail icon | `entry` = an HTML file in the bundle; `side` = `left`/`right`/`bottom`. `right` also surfaces in the chat session's right rail and the Company sidebar. Optional `icon` from a small lucide allowlist (`cloud`, `database`, `box`, `container`, `globe`, `server`, `terminal`, `zap`, `hard-drive`, `key-round`, `package`; fallback: puzzle). Omit `activation` to surface everywhere (account-level plugins, e.g. Cloudflare/Podman). |
| `contributeCommand` | Command Palette (`Ctrl+Shift+P`) | — |
| `contributeTheme` | "Apply theme: X" in the palette | Overrides shadcn CSS vars; toggles `.dark`. |
| `contributeProjectModule` | Project/module facet | Declares IntelliJ-style project modules activated by files/deps, with nested actions/status/run configs. |
| `contributeEditorAction` | Editor/Search Everywhere command + optional gutter glyph | Can call a contributed tool through `runsTool`, pass static `toolArgs`, and target documents declaratively; active only when its activation rule matches. |
| `contributeStatusBarItem` | IDE status bar | Lightweight project/module indicator; optional click-through to `runsTool`. |
| `contributeRunConfiguration` | Project run config | Declarative command/args/kind metadata for project and module runners. |
| `contributeProvider` | LLM provider metadata | Declares the provider shape for Admin/seed/pricing. Bundled first-party providers can also export `providerAdapter` for V2 owned runtime. |
| `.mcp.json` / `skills/` | Agent MCP servers / skills | Registered on install (Claude Code convention). |

Project/module contributions use the same declarative `activation` rules as tool windows. The host
evaluates them without running plugin code, so a plugin can behave like several small IDE modules:

```ts
export default definePlugin({
  modules: [
    contributeProjectModule({
      id: 'cloudflare-worker',
      title: 'Cloudflare Worker',
      activation: {
        whenFiles: ['wrangler.toml', 'wrangler.jsonc'],
        whenPackageDep: ['wrangler', '@opennextjs/cloudflare'],
      },
      tools: ['cf_detect', 'cf_deploy'],
      editorActions: [
        contributeEditorAction({
          id: 'cf-deploy-project',
          label: 'Cloudflare: Deploy Project',
          runsTool: 'cf_deploy',
          scope: 'project',
        }),
      ],
      statusBarItems: [
        contributeStatusBarItem({ id: 'cf-project', label: 'Cloudflare', alignment: 'right' }),
      ],
      runConfigurations: [
        contributeRunConfiguration({
          id: 'cf-dev',
          title: 'Cloudflare Dev',
          command: 'npx',
          args: ['wrangler', 'dev'],
        }),
      ],
    }),
  ],
});
```

Editor actions can also render a host-owned glyph in Monaco without giving plugin code access to the
editor process. `activation` selects the project/module on the host; `documentSelector` selects the
open document in the renderer. When both file and language selectors are present, both must match.
The line matcher is a small literal DSL (`equals`, `startsWith`, `contains`, `word`) rather than a
plugin-provided regular expression.

```ts
contributeEditorAction({
  id: 'podman-build-containerfile',
  label: 'Podman: Build Image',
  runsTool: 'podman_project_run',
  toolArgs: { buildOnly: true },
  scope: 'editor',
  documentSelector: {
    filePatterns: ['Dockerfile', 'Dockerfile.*', 'Containerfile', 'Containerfile.*'],
    languageIds: ['dockerfile'],
  },
  gutter: {
    line: { text: 'FROM', match: 'word', trim: true, caseSensitive: false },
    occurrence: 'first',
    icon: 'build',
    tooltip: 'Build this image with Podman',
  },
});
```

On a gutter click the IDE invokes `runsTool` with `toolArgs` plus a reserved `_editor` object:
`{ path, languageId, lineNumber, column, lineText }`. The buffer is never sent. The worker still runs
through the normal plugin capability boundary and receives project identity through `ctx`.

### Provider plugins

Provider plugins have two layers:

- `providers: [ProviderSpec]` is still pure metadata. It drives Admin, model defaults, pricing,
  visual identity, config fields and initial validation.
- `export const providerAdapter = defineProviderAdapter(...)` or
  `defineProviderAdapterFromSpec(...)` is executable V2 runtime. The host registers a normal
  `ProviderDefinition`, but credential resolution, OAuth refresh, model discovery, test connection
  and client creation dispatch into the plugin bundle.

The host still owns encrypted token persistence and the registry lifecycle; the plugin owns the
provider-specific decisions.

```ts
import { definePlugin, contributeProvider } from '@mcp/plugin-sdk/define.js';
import { defineProviderAdapterFromSpec } from '@mcp/provider-engine/plugin-adapter.js';
import { myProviderSpec } from './spec.js';

export const providerAdapter = defineProviderAdapterFromSpec(myProviderSpec, {
  async resolveCredentials({ config, credentials }) {
    const stored = await credentials.get();
    return {
      apiKey: stored?.access_token ?? config.api_key ?? undefined,
      baseURL: config.base_url ?? myProviderSpec.defaultBaseURL,
      extra: config.extra ?? undefined,
    };
  },
});

export default definePlugin({
  providers: [contributeProvider(myProviderSpec)],
});
```

When the CLI sees `providerAdapter`/`providerAdapters`, it writes:

```json
{
  "providerRuntime": {
    "protocol": "provider-adapter-v2",
    "entry": "./dist/plugin.js",
    "kinds": ["my-provider"]
  }
}
```

For security, executable provider adapters are currently activated only for bundled first-party
plugins. Third-party provider plugins continue through the declarative V1 path until signed runtime
permissions are promoted.

## How it works

**Install** — `plugins.install({ source })` materializes the bundle to
`{dataDir}/plugins/{namespace}/`, validates `plugin.json`, then applies each component: skills →
`SkillStore`, MCP servers → `McpServerStore`, contributions snapshot → the `installed_plugins` row
(migration 112). Sources: `{source:'local',path}`, `{source:'github',repo}`,
`{source:'market',name}`. `plugins.uninstall` tears everything down by namespace.

**Agent execution** — per run, the http-api reads enabled plugins, builds `pluginTools`
(`buildPluginTools`) and passes them to `runCoder`. Each handler dispatches to a
**`PluginWorkerHost`** — a `worker_thread` that dynamic-imports the plugins' `dist/plugin.js` and
runs handlers off the main loop, with a reverse `host.invoke` channel. Worker threads isolate
crashes/memory; hard FS sandboxing (Node permission model) is a future hardening step.

**UI** — on workspace mount, `hydrateContributions()` loads `plugins.list` into a Zustand registry;
rail items + tool windows merge with the built-ins. Tool windows render via `WebviewWindow` —
`<iframe sandbox="allow-scripts">` with `srcDoc` fetched through `plugins.readAsset` (confined to
the plugin dir). The iframe reaches the host only through `webview-bridge`, which forwards a
**whitelist of read-only** api-bus methods.

**RPC** — the `plugins` api-bus namespace: `list · get · install · uninstall · setEnabled ·
readAsset · searchMarket · marketInfo`, mounted as `api:plugins:*`.

## UI Kit (webviews)

Build webview UIs with **`@mcp/plugin-sdk/ui`** — a small, framework-agnostic helper library
(vanilla TS, the host's React can't run in a null-origin iframe). It renders the polished `.mcp-*`
kit so plugins look native and consistent (the Podman and Cloudflare plugins are built on it).

```ts
import { masterDetail, pageHeader, dataTable, status, icon, mcp } from '@mcp/plugin-sdk/ui';

const root = document.getElementById('root'); // <div id="root" class="mcp-app">
root!.appendChild(masterDetail({
  items: [{ id: 'containers', label: 'Containers', icon: 'box', group: 'Compute' }],
  active: 'containers',
  renderContent: (host) => {
    host.appendChild(pageHeader({ title: 'Containers', primary: { label: 'Run', icon: 'play', onClick: run } }));
    host.appendChild(dataTable({
      columns: [
        { header: 'Name', cell: (c) => c.name },
        { header: 'Status', cell: (c) => status(c.running ? 'ok' : 'muted', c.state) },
      ],
      rows, rowKey: (c) => c.id,
      actions: [{ icon: 'square', title: 'Stop', onClick: stop }, { icon: 'trash-2', title: 'Remove', danger: true, onClick: rm }],
    }));
  },
}));
```

Key exports: `masterDetail` / `navRail` / `pageHeader` / `statTiles` (layout), `dataTable` + `status`
+ `autoTable` (tables), `listView` / `detailHeader` / `tabsBar`, `state` / `loadingBox` / `emptyBox`
/ `errorBox`, `streamLog`, `icon` (inline lucide subset), `el` / `div` / `button` / `iconBtn` /
`input` / `field` (DOM), `call` / `mutate` / `toast` / `confirmDanger` (tool calls), `mcp` (the typed
`window.mcp`), and `KIT` (the `.mcp-*` class names, for hand-written markup). For non-English UIs call
`configureKitLabels({ … })` once at boot so the builders' built-in strings ("Create", "Loading…", …)
localize too.

> **Early `window.mcp` calls are safe.** The shim buffers tool calls during boot until the host
> registers the frame and posts `ready`, so calling `mcp.invokeTool(...)` at startup can't race the
> registration (the old "frame not registered" error).

### The kit CSS (runtime-injected, append-only)

The host injects a themed stylesheet (`<style id="mcp-ui-kit">`, see
`apps/dashboard/features/workspace/plugin-ui-kit/`) into **every** plugin webview, right after
`<head>` opens — so your own `<style>` (later in the head) overrides any kit rule by plain cascade
order. Every selector is namespaced `.mcp-*`; plugins that style raw elements are untouched. The kit
is themed by the host CSS variables (`--background`, `--primary`, `--border`, `--success`, …), so it
always matches the active theme. It is **runtime-injected and append-only — never bundle or vendor
the CSS**; a plugin built against any kit version keeps working as the host adds classes.

## Security model

- **Tool code** runs in an isolated worker thread; the handler context exposes only `fetch`, `log`,
  and a brokered `host.invoke`.
- **Webview UI** runs in a null-origin sandboxed iframe (`allow-scripts`, no `allow-same-origin`) —
  no access to host DOM/cookies/storage; its only channel is the read-only bridge.
- **Market bundles are Ed25519-signed**: the worker signs `sha256(zip)` at publish; the host
  re-hashes the download and verifies against the pinned `MCP_MARKET_PUBKEY` **before** extracting.
- **Asset reads** are confined to the plugin dir (path traversal rejected); manifest paths reject
  `..`/absolute at the schema boundary.

## Hosted Market

`worker-market/` is a Cloudflare Worker — **D1** catalog + **R2** bundles + **Ed25519** signing.

```bash
cd worker-market && npm install
node scripts/keygen.mjs                         # prints the Ed25519 keypair
wrangler d1 create plugin-market                # paste database_id into wrangler.jsonc
wrangler r2 bucket create mcp-plugin-bundles
npm run schema                                  # apply schema.sql to D1
wrangler secret put AUTH_TOKEN                  # publish auth
wrangler secret put MARKET_SIGNING_PRIVKEY      # base64 pkcs8 from keygen
wrangler deploy
```

> The keygen prints two values: the **PEM public key** (set as `MCP_MARKET_PUBKEY` on the host)
> and the **base64 private key** (feed ONLY to `wrangler secret put MARKET_SIGNING_PRIVKEY` —
> never paste it into a file or commit it).

On the host/IDE, set: `MCP_MARKET_URL` (deployed worker URL), `MCP_MARKET_PUBKEY` (PEM public key
from keygen — used to verify bundles), `MCP_MARKET_TOKEN` (publish token).

Endpoints: `GET /plugins?q=` · `GET /plugins/:name` · `GET /bundle/:name/:version` (zip +
`X-Signature`) · `POST /publish?name=&version=` (Bearer).

## End-to-end smoke

1. `mcp-plugin create demo && cd demo && mcp-plugin build .`
2. Install: `plugins.install({ source: { source: 'local', path: '<abs>/demo' } })` (or publish to
   the Market and install with `{ source: 'market', name: 'demo' }`).
3. In the Workspace: the plugin's rail icon opens its webview; the palette lists "Apply theme: …";
   start a chat and the agent can call `plugin__demo__echo`.
